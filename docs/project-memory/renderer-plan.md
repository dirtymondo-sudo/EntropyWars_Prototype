**Facts worth keeping:**
- R2 (2026-10-02) loads ONE copy of three@0.186.1 as ES modules: index.html import map + an inline module shim that builds `window.THREE` (a plain copy of the namespace + the jsm add-ons under the examples/js names) and sets `ColorManagement.enabled = false`; every game `<script src>` is `defer`; three inline blocks are modules. Never re-add classic three script tags.
- The look is kept by three-renderer.js `_ewLegacyLightPatch` (× π + linear fall-off + decay 1 patched into `lights_pars_begin`; PointLight/SpotLight subclassed) and `outputColorSpace = Linear` on the board renderer. `_ewTexSetSRGB` / `_ewTexIsSRGB` wrap encoding ↔ colorSpace; never write `.encoding` again.
- r186 gotchas found only by the load check: `vUv` is declared only for anisotropy (hooks need their own varying; maps use `vMapUv`); `boneTransform` is gone (`applyBoneTransform`), so `typeof` gates on old names silently drop a path; PCFSoftShadowMap removed; THREE.Clock deprecated; `THREE.Pass` is a class (`Pass.call(this)` throws).
- Import map FIRST: nothing module-related (modulepreload links, module scripts) may precede it or Firefox voids the map (bare `three` unmapped → no window.THREE → raw party builder DOM, no title; PR #50 hotfix 2026-10-02). Chromium tolerates the wrong order, so sandbox checks never catch it; mondo plays in Firefox on a Mac.
- Ranked add-ons: KTX2 (R3), three-mesh-bvh (R4), pmndrs postprocessing (R5), troika-three-text (R6), three.quarks (R7, only if the lens shows particle cost). BatchedMesh for the static batch = R2b.
